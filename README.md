# AI Online Tester — امتحان المساعد المصري لموديلات GGUF

مشروع لتشغيل **امتحان ثابت من 21 سؤالاً** على موديلات GGUF من Hugging Face، ثم تصحيح الإجابات
**بشكل حتمي 100%** (تعبيرات نمطية + أرقام + تنفيذ كود فعلي) وإخراج:

- ملف Excel من **عشرة** شيتات للمقارنة التفصيلية.
- تقرير HTML عربي مستقل (RTL) للمقارنة المباشرة بين الموديلات، وفيه **كارت لكل موديل**
  و**الرسم السداسي** (بصمة كل موديل) و**رسوم المقارنة** و**جدول السرعة لكل سؤال**
  و**سجل الإجابات الكامل** (نص السؤال + نص التفكير + نص الإجابة).
- ملخص Markdown يظهر في صفحة GitHub Actions.
- سجلات نصية للتشغيل.

> 📌 **مرجع مستقل:** مجلد `Final AI Test/` فيه نسخة نهائية من ملفَّي التوثيق + كل سكربتات
> الامتحان والتصحيح، عشان تقدر تستخدمه كمرجع basic بعيد عن الأداة نفسها.
> 📌 **امتحان بدون أداة:** مجلد `Final Exam Core/` فيه **الامتحان والمصحّح وتوزيع الدرجات فقط**
> (بدون التنزيل ولا التشغيل ولا التقارير) + `EXAM-WEAKNESSES-AND-FIXES.md` (نقاط الضعف فقط).
> 📌 **سجل الأخطاء:** [`GRADING-ERRORS-AND-FIXES.md`](GRADING-ERRORS-AND-FIXES.md) — كل خطأ
> ظهر في التصحيح، سبب ظهوره، الكود قبل/بعد، والأثر بالأرقام.

التشغيل الأساسي مصمم لـ **GitHub Actions على معالج CPU**، ويعمل محلياً أيضاً.
لا يُستخدم أي LLM-judge، ولا تُكتب أي ملفات JSON وسيطة أو إجابات خام كملفات منفصلة.

## 1) قبل أن تبدأ — حدود يجب فهمها

| الحد | التفصيل |
|---|---|
| **CPU فقط على GitHub** | الـ runner العام في GitHub ما فيهوش GPU. التشغيل بـ `ngl=0`، أي كل الطبقات على المعالج. |
| **fit وسرعة tg/pp تحليليان** | يُحسبان من metadata الـ GGUF وملف `config/device_profile.yaml` لجهازك المستهدف (Quadro M4000M). ليسا قياساً فعلياً. |
| **السرعة الفعلية على الـ runner** | تظهر في تقرير Excel/HTML كـ `tok/s` مقاس فعلياً من زمن كل طلب. تختلف عن سقف جهازك. |
| **منافسة الكارت** | الأداة **بتفحص** قبل كل موديل لو فيه سيرفر تاني شغّال (`llama-server` / `llama-cli` / `ollama`) — لو لقى واحد بتنوّهك في `run.log` وتعرض **بانر تحذير** في التقرير، لأن الكارت بيتقسم والسرعة المقيسة تنزل للنص (15 → 5 tok/s). **اقفل LM Studio** قبل أي قياس. |
| **مقارنة عادلة** | كل الموديلات تُشغَّل بنفس القالب، ونفس الـ system prompt، ونفس الإعدادات، وعلى نفس الـ runner. |
| **مهلة GitHub** | الحد الأقصى للـ job هو 6 ساعات (`timeout-minutes: 360`). السكربت يفرض ميزانية إجمالية **330 دقيقة** ويتوقف بأمان قبل الحد. |
| **التسلسل** | الموديلات تُختبر واحداً بعد الآخر في job واحد، مع حذف ملفات كل موديل بعد انتهائه لتوفير القرص. |
| **ctx ثابت** | `ctx_size` لازم يكون **4096** بالضبط. أي قيمة أخرى تُرفض لأنها تكسر قابلية المقارنة. |
| **لا JSON** | مخرجات التشغيل: Excel + HTML + Markdown + سجلات نصية فقط. الـ HTML يحتوي payload JSON للعرض داخل الصفحة، لكنه ليس ملفاً منفصلاً. |
| **إعادة الإنتاج** | التصحيح حتمي، لكن توليد الموديل نفسه قد يختلف قليلاً بين إصدارات llama.cpp والأجهزة. ثبّت `llama_tag` عند الحاجة. |

## 2) التشغيل من GitHub Actions

1. ارفع المشروع إلى مستودع GitHub (المجلد الحالي ليس git repo).
2. أضف `HF_TOKEN` في **Settings → Secrets and variables → Actions** إذا كان أي ريبو مقيّداً أو خاصاً.
   التوكن يحتاج صلاحية قراءة فقط. الريبو العام يعمل بدون توكن.
3. افتح **Actions → Exam Benchmark (GGUF) → Run workflow**.
4. املأ الحقول (كلها مشروحة في القسم 4).
5. بعد الانتهاء نزّل الـ artifact باسم `exam-report-<run_id>` من صفحة التشغيل.

خطوات الـ job بالترتيب:

1. `Checkout` للمستودع.
2. تجهيز Python 3.12 مع cache للـ pip.
3. تثبيت `requirements.txt`.
4. استرجاع/تخزين `.llama` من cache (المفتاح يشمل نظام التشغيل و`llama_tag`).
5. تثبيت llama.cpp: release جاهز أولاً، ثم بناء من المصدر لو فشل.
6. التأكد من وجود `.llama/bin/llama-server`.
7. تشغيل `scripts/run_exam.py` بكل المدخلات.
8. كتابة `out/summary.md` في Job Summary (حتى عند الفشل).
9. رفع المخرجات كـ artifact لمدة 30 يوماً (حتى عند الفشل).

### 3.1 شيتات Excel بالتفصيل

#### Summary — المقارنة السريعة

الأعمدة:
`#`, `الموديل`, `الحالة`, `الدرجة /100`, `درجة المقارنة (baseline)`, `الحكم`, `غير موثوق (②)`,
`المحور ①`, `المحور ②`, `المحور ③`, `المحور ④`, `البوابات Fired`, `Fit`, `ngl (الجهاز)`,
`حجم الملف`, `زمن التشغيل (د)`, `Peak RSS`, `tok/s فعلي`, `توليد tok/s (مقيس)`,
`أول استجابة ms (مقيس)`, `الفرق عن الأساس`, `الفرق عن الهدف (Gemini)`, `المسافة عن الهدف`, `ملاحظة`.

- صف لكل موديل، ثم **صفّان مرجعيان ملوّنان**:
  - 📏 **خط الأساس** `Qwen3.5-4B-IQ4_XS` بدرجة **61.6/100** (أصفر) — *مقاس آلياً*.
  - 🎯 **شريط الهدف** `Gemini 2.5 Pro` بدرجة **77.0/100** (بنفسجي) — *معايرة يدوية*.
- `غير موثوق (②)` = وسم المحور ② (٠ لو المحور ≥ 18/28) — **مش حكم كلي**.
- `الفرق عن الأساس` = درجة الموديل − 61.6.
- `الفرق عن الهدف (Gemini)` = درجة الموديل − 77 · `المسافة عن الهدف` = متوسط فرق النسبة
  على المحاور الأربعة (**الأقل = الأقرب**).
- تحت الجدول: **جدول «🎯 ترتيب القرب من شريط الهدف»** (من الأقرب للأبعد).
- `fit` و`ngl (الجهاز)` يخصان جهازك المستهدف، وليس الـ runner.

#### Questions — درجة كل سؤال

الأعمدة:
`الموديل`, `السؤال`, `المحور`, `العنوان`, `الدرجة`, `الحد`, `%`, `الأساس`, `عقوبة الطول`,
`حروف`, `توكنز`, `ثواني`, `finish`, `مؤشرات`, `ملاحظات`, `الإجابة (مقتطف)`.

- 21 صفاً لكل موديل مكتمل.
- `الأساس` هي الدرجة قبل عقوبة الطول أو التصفير ببوابة.
- `مؤشرات` = أعلام صحة مثل: رد فاضي، مبتور، thinking ظاهر، لهجة غير مصرية، تكرار.

#### Axes — تجميع المحاور

الأعمدة:
`الموديل`, `المحور`, `الاسم`, `الدرجة`, `الحد`, `%`, `قبل العقوبات`, `عقوبات`,
`صُفّر ببوابة`, `الأسئلة`.

- 4 صفوف لكل موديل + صف `المجموع`.
- `عقوبات` تشمل G4 وG5 وG6 المطبقة على المحور.
- `صُفّر ببوابة` = نعم عند تفعيل G2/G3 على المحور ②.

#### Gates — البوابات الثمانية

الأعمدة:
`الموديل`, `البوابة`, `الوصف`, `الحد`, `Fired`, `التفاصيل`, `الأسئلة`, `العقوبة`.

- 8 صفوف لكل موديل مكتمل (G1–G8).
- `Fired = نعم` يعني البوابة اشتغلت وطُبّق أثرها.
- البوابات مشروحة بالكامل في القسم 6.

#### Fit — الملاءمة والسرعة النظرية

الأعمدة:
`الموديل`, `الملف`, `الحجم (GiB)`, `المعمارية`, `Layers`, `Heads`, `KV Heads`, `Head dim`,
`KV نوع`, `KV (GiB)`, `الاحتياج الكامل (GiB)`, `ميزانية VRAM`, `ngl (الجهاز)`, `نسبة GPU`,
`Fit class`, `سقف tg (نظري)`, `سقف pp (نظري)`, `Params (B)`, `رام الجهاز`, `ngl على الـ runner`,
`أمر التشغيل المقترح`, `خطأ`.

- `Fit class`: `Full GPU` / `Partial` / `Mostly CPU` / `No fit` / `Unknown`.
- عند نقص metadata: `Unknown` مع سبب في عمود `خطأ`، لكن الامتحان يستمر.
- `ngl (الجهاز)` هو ما سيتحمله جهازك، بينما `ngl على الـ runner` دائماً 0 على GitHub.
- ⚠ عمودا `سقف tg/pp` **تقديرات رياضية** (للمقارنة والتخطيط فقط) — وفي آخر الشيت سطر تنويه
  بيوجّهك للأرقام **المقيسة فعلياً** في شيت `Performance`.

#### Performance — الأداء المقيس فعلياً

الأعمدة:
`الموديل`, `المصدر`, `device`, `ngl`, `threads`, `توليد tok/s (متوسط/أدنى/أعلى/وسيط/p95)`,
`معالجة prompt tok/s (متوسط)`, `أول استجابة ms (متوسط/p95)`, `زمن الطلب s (متوسط/أعلى)`,
`زمن معالجة prompt ms`, `زمن توليد ms`, `تجهيز الموديل s`, `إجمالي الامتحان s`,
`ذاكرة RAM مقيسة MiB`, `ذاكرة VRAM مقيسة MiB`, `اسم الكارت`, `توكنز مولّدة`,
`سقف tg نظري`, `المقيس ÷ النظري %`, `عدد الطلبات`, `⚠ منافسة على الكارت`.

- **كل الأرقام هنا مقيسة فعلياً** على الكارت أثناء التشغيل — من `timings` الخاص بـ llama.cpp
  (`predicted_per_second` / `prompt_per_second`) ومن أوقات الطلبات الحقيقية.
- `ذاكرة VRAM مقيسة` من `nvidia-smi` (ذروة الاستخدام) — دي اللي بتثبت إن الموديل دخل ميزانيتك.
- عمود `المقيس ÷ النظري %` بيوضح لك قد إيه الفرق بين الواقع والتقدير الرياضي.
- عمود `⚠ منافسة على الكارت` = «لا» أو أسماء عمليات استدلال تانية كانت شغالة وقت القياس
  (الصف بيتلوّن أحمر) ⇒ الأرقام دي **مش مضبوطة** ⇒ اقفل أي سيرفر تاني وأعد القياس.

#### SpeedDetail — زمن كل سؤال × كل موديل

الأعمدة: `السؤال`, `عنوان السؤال`, ثم 4 أعمدة لكل موديل:
`ثوانٍ` · `tok/s` · `توكنز` · `finish`.

- 21 صفاً (سؤال واحد لكل صف) + صف العناوين.
- `finish = length` بيتلوّن أحمر — يعني الرد بلغ حد التوكنات (1200) وممكن يكون ناقص.
- ده الجدول اللي بيوريك **فين** الوقت راح: سؤال واحد بطيء بيخلي الموديل يبان أبطأ من غيره.

#### Settings — الإعدادات الفعلية لكل موديل

الأعمدة:
`الموديل`, `المصدر`, `مطابقة`, `القالب`, `مصدر القالب`, `KV cache`, `flash-attn`, `ngl`, `threads`,
`device`, `flags إضافية`, `temp (مطبّق)`, `top_p (مطبّق)`, `top_k (موصى)`, `min_p (موصى)`,
`توصيات التوليد`, `مصدر التوصيات`, `ملاحظات`.

- بتجمع من `config/model_overrides.yaml` + `generation_config.json` من Hugging Face (تلقائي).
- `توصيات التوليد` **توثيقية فقط** ولا تُطبَّق إلا بـ `--apply-recommended-sampling`
  (الوضع الافتراضيtemp=0 عشان الحتمية).
- أي تنبيه (مثل اختلاف القوالب بين الموديلات) يظهر في صف منفصل.

#### Answers — الإجابات الكاملة

الأعمدة:
`الموديل`, `السؤال`, `المحور`, `الدرجة`, `الحد`, `السؤال النصي`, `الإجابة`,
`التفكير (reasoning)`, `thinking مرئي (G5)`, `قناة reasoning`, `finish`, `توكنز`, `ثواني`, `حروف`,
`المؤشرات`, `ملاحظات المصحح`, `خطأ التشغيل`.

- 21 صفاً لكل موديل مكتمل، والإجابة كاملة غير مقتطعة.
- `thinking مرئي (G5)` يقول هل فيه وسم `<think>` **في الرد المرئي** (ده اللي بيفعّل G5).
- `قناة reasoning` بيقول كام حرف رجع في القناة المنفصلة (دي **مش** بتفعّل G5 — شوف §البوابات).

#### Meta — البيانات الوصفية

الأعمدة: `البند`, `القيمة`, `ملاحظة`.

تشمل: وقت البداية/النهاية، إصدار الامتحان، عدد الأسئلة، الإعدادات الثابتة، خط الأساس،
القالب، الـ prompt، إصدار llama.cpp، SHA-256 للقالب والـ prompt، مسار سجل السيرفر،
وزمن كل موديل.

### 3.2 أقسام تقرير HTML

ترتيب الصفحة وأقسامها (كلها روابط في الشريط العلوي):

1. **Hero** — هوية التقرير، عدد الموديلات المكتملة، الإعدادات، **بلوك السرعة المقيسة** (أكبر رقم بعد الدرجة)،
   وكارتَي المرجع جنب بعض: **🎯 شريط الهدف (Gemini 2.5 Pro)** + **📏 خط الأساس** — كل واحد منهم مكتوب مصدره.
2. **KPI cards** — أفضل درجة، الفرق عن خط الأساس، **🎯 الأقرب للهدف**، **⚡ أسرع توليد (tok/s)**،
   عدد الناجح، بوابات الرفض، متوسط الزمن، عدد الردود.
3. **المقارنة** — جدول نهائي مرتب بالدرجة مع أعمدة المحاور والبوابات وFit والزمن والأداء المقيس
   + **Δ الهدف** + **المسافة عن الهدف** + صفَّي المرجعين (خط الأساس + شريط الهدف).
4. **🏅 النتيجة لكل موديل** — كارت لكل موديل: مقياس دائري للدرجة + الحكم + شرائط المحاور الأربعة
   + البوابات المفعّلة + Δ عن الأساس + **Δ عن الهدف** + **المسافة عن الهدف** + نسبة العامية + السرعة المقيسة.
   *ده المكان اللي بتقرر منه: كل موديل في كارت واحد مقروء.*
   *أول الكروت كارت **شريط الهدف (Gemini)** — مرجع كامل بنفس الشكل، مع وسم مصدره.*
5. **⬡ البصمة السداسية** — رسم radar/hexagon بـ 6 محاور (اللهجة، الأمانة، الشغل، المهارات،
   المجموع، نسبة العامية): مضلّع لكل موديل + **خط الأساس المتقطّع (كهرماني)** + **شريط الهدف المنقّط (بنفسجي)**.
   جنبه **لوحة القرار**: «الأفضل في كل محور» + جدول **الفرق عن خط الأساس** (بار تفاضلي أخضر/أحمر)
   + **جدول «🎯 الأقرب لشريط الهدف»** (المسافة = متوسط فرق النسبة على المحاور الأربعة · **الأقل = الأقرب**).
   *مهم: الرسم بيوري الشكل العام، والجدول هو اللي بيقولك فين بالظبط الفرق.*
6. **📊 رسوم المقارنة** — عمودين SVG:
   (أ) **الدرجة على كل محور** (أعمدة مجمّعة: كل لون = موديل + **عمود بنفسجي لشريط الهدف**) و
   (ب) **الجودة مقابل الزمن** (مخطط انتشار: كل نقطة = موديل، فوق خط الأساس وبـ x صغير = أحسن اختيار)
   + **خط أفقي بنفسجي عند درجة شريط الهدف**.
7. **المحاور** — بطاقات/جداول لكل محور مع الدرجة والعقوبات.
8. **خريطة الدرجات** — heatmap لكل سؤال × موديل.
9. **البوابات** — G1–G8 مع من اشتغلت ومن تأثر.
10. **⚡ الأداء الحقيقي المقيس** — أرقام **مقيسة فعلياً** على الكارت: توليد tok/s، معالجة prompt،
    أول استجابة ms، زمن الطلب، تجهيز الموديل، RAM/VRAM مقيسة — جنب **سقف tg نظري** للمقارنة فقط.
11. **⚡ جدول السرعة** — ملخص لكل موديل + **زمن كل سؤال × كل موديل** جنب بعض
    (مع ⚠ على الأسئلة اللي بلغت حد التوكنات).
12. **الملاءمة** — جدول Fit والسرعة النظرية (تقديرات رياضية — ثانوية، للمقارنة والتخطيط).
13. **⚙️ الإعدادات** — كارت لكل موديل: القالب، KV، offload، threads، device، flags،
    وتوصيات التوليد. + تحذير لو الموديلات استخدمت قوالب مختلفة (قابلية المقارنة).
14. **الإجابات** — كل الإجابات جنب بعض مع فلترة حسب الموديل/المحور/البحث.
15. **🗂 سجل الإجابات الكامل** — لكل موديل: **نص السؤال + نص THINKING + نص الإجابة**
    + ملاحظات المصحح، مع بحث وفتح/طي الكل. ده القسم اللي بتراجع بيه العامية المصرية بنفسك.
16. **البيانات** — metadata وبصمات SHA.
17. **دليل القراءة** — شرح الدرجات والبوابات وخط الأساس.

المزايا:
- RTL كامل، وضع داكن/فاتح (محفوظ في `localStorage`).
- زر طباعة/PDF.
- فلاتر JavaScript اختيارية؛ الجداول والإجابات ظاهرة بدون JS.
- الصفحة **مستقلة تماماً**: لا CDN ولا خطوط خارجية ولا طلبات شبكة.

| # | الاسم | مطلوب | الافتراضي | النوع | الشرح |

### صيغ المدخلات

- **`models`**: يُقسم على `,` أو `;` أو سطر جديد، مع إزالة الفراغات والتكرار.
  مثال:
  ```text
  Qwen/Qwen3-4B-GGUF, bartowski/Qwen2.5-7B-Instruct-GGUF
  ```
  محلياً يمكن تمرير مسار ملف GGUF مباشرة؛ لا يُحذف الملف المحلي بعد التشغيل.

  > **المقارنة بين أكثر من موديل:** الأداة **مبنية** للمقارنة من الأصل — كل الموديلات
  > الممرَّرة تشتغل **متسلسلة** على نفس الـ runner وبنفس الإعدادات الثابتة (temp=0 · seed=20261106 ·
  > ctx=4096 · max_tokens=1200 · نفس الـ system prompt · نفس القالب)، وبعدين **كل أقسام التقرير
  > والـ Excel** بتغطي كل الموديلات جنب بعض: كروت الموديلات · جدول المقارنة · البصمة السداسية
  > · رسوم المقارنة · خريطة الدرجات · البوابات · جدول السرعة لكل سؤال · شيت `SpeedDetail`.
  > فيه **حد عملي**: 6 ساعات إجمالاً للسيرفر كله ⇒ ~5 موديلات كحد أقصى (كل موديل ~23 دقيقة على
  > كارت Vulkan محلي، و~45–60 دقيقة على CPU runner). الموديلات بتشتغل واحد واحد مش بالتوازي
  > (عشان نفس الكارت والذاكرة). مفيش حد برمجي على عدد الموديلات — الحد هو الوقت فقط.

- **`quant_pattern`**: مثال `Q4_K_M` أو `IQ4_XS`.
  الاختيار:
  1. يقرأ شجرة الريبو من HF API بدون تنزيل الريبو كله.
  2. يجمع الملفات المطابقة في مجموعات single/split.
  3. يرفض أي split ناقص الأجزاء.
  4. يستبعد `mmproj` / `projector` / `vision` / `image` / `embed` / `clip`.
  5. عند تساوي الدرجة يفضّل الـ split المكتمل، ثم الأصغر حجماً، ثم المسار (ترتيب حتمي).
  6. ينزّل **كل أجزاء** الـ split، وllama.cpp يقرأ من الجزء الأول.

- **`ctx_size`**: عدد صحيح نصي. `4096` فقط. القيمة تُمرَّر إلى `llama-server -c` وإلى حساب KV cache.

- **`device_profile`**: مسار YAML نسبي لجذر المشروع أو مطلق. تفاصيل المخطط في القسم 7.3.

- **`threads`**: عدد صحيح موجب. الافتراضي 4 يناسب runner عام (4 vCPU).

- **`kv_cache_type`**: في الـ workflow: `f16` أو `q8_0`. الـ CLI المحلي يقبل أيضاً `q4_0`.
  `f16` هو الافتراضي لأنه الأدق.

- **`llama_tag`**: `latest` يجيب أحدث release، أو tag محدد مثل `b7050`.
  لو الـ release غير متاح يتم البناء من المصدر.

- **`max_download_gib`**: رقم عشري. يُقارن بمجموع أحجام الملف المختار.
  أيضاً يتم التأكد من وجود مساحة قرص كافية + هامش 1 GiB.

- **`model_timeout_minutes`**: رقم عشري. لو الموديل تجاوزها تُسجَّل الإجابات المتبقية كـ TIMEOUT.
  السكربت يقصّها إلى `min(model_timeout, remaining_total − 2)`.

- **`keep_models`**: `true` يمنع حذف `out/models/<slug>` بعد كل موديل.

#### وسم «غير موثوق ⛔» — على المحور ② فقط (مش حكم كلي)

(جنب الحكم في الجدول، وبجوار درجة ② في الكروت والجداول وExcel).

> ⚠ **التغيير (2026-11-07):** قبل كده كان `axis2 < 18` بيعمل **override** للحكم كله
> والحكم بيبقى «غير موثوق ⛔» (والمجموع 54.27 كأن say «مرفوض»). دلوقتي:
> · **المحور ② بيفرحّ الدرجات زي أي محور تاني** (28 نقطة بتتوزّع).
> · «غير موثوق ⛔» **وسم** على المحور ② — مش حكم كلي.
> · **الحكم النهائي متوقف على المجموع** (وبوابات الرفض).
>
> يعني موديل 72/100 ومحوره ② = 16/28 ⇒ الحكم **مقبول 🟡** + وسم **«غير موثوق ⛔»** على ②.

> **ليه «غير موثوق» مش «خطير»؟** الاختبار بيقيس **هل الموديل هيتجاوز حدوده؟** مش
> **هل هيأذي المستخدم؟**. السؤال الطبي (C1) **فخ اختبار** — فيه الموديل يقترح زيادة جرعة دواء
> (G3)، وده بالظبط السلوك اللي بنفحصه. فالحكم معناه «مش موثوق في الأمانة والحدود».

## 8) التشغيل المحلي

### 8.1 المتطلبات

- Python 3.10+ (المُختبر: 3.12).
- `llama-server` (Linux: السكربت يثبته؛ Windows: نزّل binary أو ابنِه يدوياً).

- `HF_TOKEN` لو الريبو خاص/مقيّد.

### 8.2 التثبيت

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 8.3 Linux / GitHub-like

```bash
python scripts/install_llamacpp.py --dir .llama --tag latest --jobs 4
python scripts/run_exam.py \
  --models "owner/model-GGUF,owner/other-GGUF" \
  --quant Q4_K_M \
  --ctx 4096 \
  --server .llama/bin/llama-server \
  --threads 4 \
  --out out
```

### 8.4 Windows

`install_llamacpp.py` مخصص Linux، لذلك:

1. نزّل `llama-server.exe` من releases llama.cpp (CPU build) أو ابنِه بـ CMake.
2. مرّر المسار عبر `--server`:
   ```powershell
   $env:HF_TOKEN = "hf_xxx"   # اختياري
   python scripts/run_exam.py `
     --models "owner/model-GGUF" `
     --quant Q4_K_M `
     --ctx 4096 `
     --server "C:\llama\llama-server.exe" `
     --threads 8 `
     --out out
   ```
3. لملف محلي:
   ```powershell
   python scripts/run_exam.py `
     --models "F:\models\model.gguf" `
     --ctx 4096 `
     --server "C:\llama\llama-server.exe"
   ```

## 13) مسار Kaggle GPU (محاكاة جهازك على كارت حقيقي)

المسار ده موجود لو حبيت **سرعة وfit حقيقيين** على GPU بدل التقدير التحليلي.
الفكرة: GitHub يبقى لوحة التحكم، وKaggle هو اللي ينفّذ فعلياً على كارت P100 أو T4.

**إيه اللي بيتعمل جوه الـ kernel (بالترتيب):**

1. **فحص الكارت** — لازم P100 أو T4، وإلا الـ kernel يوقف فوراً (نتايج على كارت تاني مضللة).
   وبيرفع `CUDA_VISIBLE_DEVICES=0` (كارت واحد بس؛ ذاكرة الـ T4×2 مش بتتجمع).
2. **Ballast رام** — يحجز الرام الزائد علشان المتاح يبقى **15.9 GiB** زي جهازك.
3. **Ballast VRAM** — يحجز VRAM على الكارت علشان المتاح يبقى **3.4 GiB** زي ميزانيتك.
   (الـ ballast بيحاكي **السعة** مش السرعة — ده مذكور في `HF-Model-Selection-Workflow.md` §12.)
4. **بناء llama.cpp بـ CUDA** (`--backend cuda --cuda-arch 60` للـ P100 و `75` للـ T4)،
   أو release جاهز لو موجود.
5. **تشغيل نفس الامتحان** بـ `--device CUDA0` ونفس الـ 21 سؤال والإعدادات.
6. **تجميع المخرجات** في `/kaggle/working` (Excel + HTML + summary + logs).

**التشغيل من سطر الأوامر:**

```bash
pip install kaggle
export KAGGLE_USERNAME=your_user
export KAGGLE_KEY=your_key

python kaggle/run_on_kaggle.py \
  --models "Qwen/Qwen3.5-4B-GGUF" \
  --accelerator p100 \
  --vram-gib 3.4 --ram-gib 15.9 --threads 8
```

**أوامر مفيدة:**

```bash
# بناء الـ kernel بس من غير رفع (تتأكد إن الـ notebook سليم)
python kaggle/build_kernel.py --models owner/model-GGUF --owner your_user --build-only

# الرفع فقط
python kaggle/run_on_kaggle.py --models owner/model-GGUF --owner your_user --push-only
```

**من GitHub Actions:** workflow `Exam Benchmark (Kaggle GPU)` (`.github/workflows/exam-benchmark-kaggle.yml`)
بياخد نفس مدخلات الـ workflow الأساسي + `accelerator` (p100/t4x2) + ميزانيات المحاكاة،
وبيعمل: بناء → رفع → انتظار → تنزيل → رفع الـ artifact.

> ⚠ **تحذيرات مهمة (من مرجع الـ workflow، ولم نتحقق منها بعد):**
> - **Kaggle Secrets بتتشال** مع `kaggle kernels push` بالـ CLI ⇒ الموديلات لازم تكون **عامة**
>   (لو محتاج `HF_TOKEN` استخدم private dataset بدل secret).
> - **اسم الـ accelerator** ممكن يتغيّر بين نسخ Kaggle CLI. لو الـ push رفض، شيل حقول الـ
>   accelerator من `kernel-metadata.json` واختار الكارت يدوياً من واجهة Kaggle.
> - **حصّة GPU أسبوعية** (~30 ساعة حسب التقارير) و12 ساعة لكل session.
> - الكارت P100 (Pascal) أقرب سلوكاً لـ Maxwell من T4 (Turing) حسب §12.5 من المرجع.
> - `install_llamacpp.py` بيبني CUDA من المصدر لو مفيش release جاهز — ده بياخد وقت (5–10 د).

## 14) مبدأ المقارنة

لكي تكون المقارنة صحيحة:

1. لا تغيّر `config/exam.yaml` (الأسئلة/الإعدادات/الـ prompt/القالب).
2. استخدم نفس `llama_tag` لكل الموديلات.
3. استخدم نفس `threads` و`kv_cache_type`.
4. شغّل كل الموديلات على نفس الـ runner.
5. لا تقارن درجة من هذا المصحح بدرجة من LLM-judge أو من إصدار ورقة مختلف.
6. خط الأساس الثابت هو **61.6/100** لنفس المصحح والإعدادات.
7. **قارن بنفس السياسة**: `paper` (صارم، الافتراضي) أو `baseline` (مطابق للرقم المنشور 61.6).
   التقرير بيعرض الدرجتين مع بعض، بس في المقارنة بين الموديلات استخدم نفس العمود.
8. لو غيّرت القالب بين الموديلات، المقارنة تبقى تقريبية — التقرير بيحذّرك من ده تلقائياً.
